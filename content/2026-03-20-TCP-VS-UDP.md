### 📡 1. L4 Fundamentals: The Core Trade-off
* **UDP (User Datagram Protocol):** Bare-bones, connectionless, and fast. It sends packets blindly without checking if the receiver is ready or if the data arrived.
  * *Real-World Example:* **Live Video Calls or Multiplayer Gaming.** If a frame or position update drops, you don't want the system to pause and fetch it; you just want the newest data immediately.
* **TCP (Transmission Control Protocol):** Reliable and connection-oriented. It guarantees that every packet arrives intact and in the correct sequence.
  * *Real-World Example:* **Loading a Bank Website or Downloading a File.** If even one byte of your bank statement drops, the entire page or file could be corrupted.

### 🤝 2. Connection Management: The Setup
* **TCP 3-Way Handshake:** Before sending any actual application data, TCP establishes a connection to synchronize.
  1.  **SYN:** Client says, "I want to talk, my starting sequence number is X."
  2.  **SYN-ACK:** Server replies, "Got it, I expect X+1. I also want to talk, my starting sequence number is Y."
  3.  **ACK:** Client confirms, "Got it, I expect Y+1. Let's send data."

### 🛡️ 3. Flow & Error Control: Guaranteeing Delivery
* **Sequence Numbers:** TCP tags every packet. If packets arrive out of order, the receiver uses these numbers to reorganize them.
* **Timeouts & ACKs:** The sender waits for an acknowledgement (ACK) for every packet. If the ACK doesn't arrive before a timeout timer expires, the sender assumes the packet was lost and resends it.

### 🚦 4. Congestion Control: Protecting the Network
* **The Sliding Window:** TCP limits how many "in-flight" (unacknowledged) packets it can send at once so it doesn't overwhelm the network infrastructure.
* **AIMD (Additive Increase, Multiplicative Decrease):** TCP constantly probes the network's speed limit. It slowly adds to the window size to go faster (Additive Increase). The moment a packet drops, it assumes the network is congested and slashes the window size in half (Multiplicative Decrease).

In a typical system design interview (like designing Instagram or a standard e-commerce site), the interviewer usually assumes you are using HTTP over TCP. You don't always need to bring it up.

However, you **must** explicitly bring up the L4 protocol choice when the system's core constraints push the limits of standard networking. Here are the main triggers:

⏱️ **1. Ultra-Low Latency / Real-Time Requirements:** If the prompt involves live video conferencing, fast-paced multiplayer gaming, or high-frequency trading tickers. This is your cue to discuss the "Latency Tax" of TCP and whether UDP is required.

📊 **2. High-Volume, Loss-Tolerant Data:**
If you are designing a system that ingests massive amounts of telemetry, analytics, or background logs. If dropping 0.1% of the data is acceptable to save massive amounts of server CPU and bandwidth, you should debate using UDP.

🛠️ **3. Low-Level Infrastructure:**
If you are asked to design a Load Balancer (L4 vs L7 routing), a custom DNS resolver, or a message queue. These systems interact directly with the transport layer, so protocol choice is the foundation of the design.
