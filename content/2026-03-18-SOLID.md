# SOLID Design Principles: 🏗️

This guide demonstrates how to design a resilient and maintainable Low-Level Design (LLD) using the five SOLID principles.

---

## 1. Single Responsibility Principle (SRP) 🎯
**Definition:** A class should have one, and only one, reason to change.

* **The Problem:** A "God Class" `Invoice` handled math (calculating tax), formatting (printing), and infrastructure (saving to a database). A change to the database server required modifying the same file used for accounting.
* **The Solution:** Extract unrelated responsibilities into dedicated classes.

```java
// 1. Core Data & Math
public class Invoice {
    private double amount;
    public double calculateTotalWithTax() { return amount * 1.10; }
}

// 2. Formatting Logic
public class InvoicePrinter {
    public void print(Invoice invoice) { System.out.println("Printing..."); }
}

// 3. Database Logic
public class InvoiceRepository {
    public void save(Invoice invoice) { System.out.println("Saving..."); }
}
```

---

## 2. Open/Closed Principle (OCP) 🚪
**Definition:** Software entities should be open for extension, but closed for modification.

* **The Problem:** The database saving logic was hardcoded to SQL. Adding MongoDB support required modifying existing, tested SQL logic.
* **The Solution:** Rely on an abstraction (Interface). We can extend the system by adding new classes without ever touching existing code.

```java
public interface InvoiceRepository {
    void save(Invoice invoice);
}

// We can add as many of these as we want without breaking OCP!
public class MongoDbInvoiceRepository implements InvoiceRepository {
    @Override
    public void save(Invoice invoice) { System.out.println("Saving to MongoDB..."); }
}
```

---

## 3. Liskov Substitution Principle (LSP) 🔄
**Definition:** Subclasses must be substitutable for their base classes without breaking the program.

* **The Problem:** A `TaxCalculator` used a massive `switch` statement to handle different invoice types (Charity, Military, Standard). If a developer instead extended the `Invoice` class and threw an exception for `calculateTotalWithTax()` on a charity invoice, it would crash the accounting loop.
* **The Solution:** Use polymorphism. The calculator trusts the object to fulfill its contract without needing to know its specific type.

```java
public interface Invoice {
    double calculateFinalAmount(); 
}

public class CharityInvoice implements Invoice {
    private double baseAmount;
    
    @Override
    public double calculateFinalAmount() {
        return baseAmount; // 0% tax, handles its own specific business rules safely
    }
}

public class TaxCalculator {
    public double calculate(Invoice invoice) {
        return invoice.calculateFinalAmount(); // Never crashes, never needs a switch statement
    }
}
```

---

## 4. Interface Segregation Principle (ISP) ✂️
**Definition:** Many specific, narrow interfaces are better than one general-purpose interface. No code should be forced to depend on methods it does not use.

* **The Problem:** A "fat" `Invoice` interface contained math methods alongside `generateDigitalPDF()` and `sendEmailReceipt()`. A `PhysicalStoreReceipt` was forced to implement email methods it couldn't actually use.
* **The Solution:** Split the interfaces by capability.

```java
public interface Invoice {
    double calculateFinalAmount();
}

public interface DigitalInvoice {
    void generateDigitalPDF();
    void sendEmailReceipt();
}

// Now the physical receipt only implements exactly what it needs
public class PhysicalStoreReceipt implements Invoice {
    @Override
    public double calculateFinalAmount() { return 100.0; }
}
```

---

## 5. Dependency Inversion Principle (DIP) 🔌
**Definition:** High-level modules should not depend on low-level modules; both should depend on abstractions.

* **The Problem:** The high-level `InvoiceService` instantiated a specific database connection directly in its constructor (`this.database = new MySQLDatabase();`), permanently coupling it to MySQL.
* **The Solution:** Use Constructor Injection to pass an abstraction into the service.

```java
public class InvoiceService {
    private final InvoiceRepository repository; // Depends on the interface

    // The specific database type is injected from the outside
    public InvoiceService(InvoiceRepository repository) {
        this.repository = repository; 
    }

    public void processInvoice(Invoice invoice) {
        repository.save(invoice);
    }
}
```
