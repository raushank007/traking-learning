# HashMap 

>HashMap = Array + LinkedList/Tree(Read-Black Tree)

Internally, a Java Hashmap is implemented as:
```java
Node<K,V>[] table // array of buckets
```
Each bucket contains
1. null -> empty bucket
2. Node -> LinkedList Node
3. TreeNode -> Red-Black tree node

This is call bucket or bin.

## What happens when we put a key? (put(k,v))

1. Compute Hash
```java
hash = key.hasCode();
```
but Java 8 improves hash distributing using "hash spreading":
```java
hash = (h)^(h>>>16)
```
Prevents collisions by mixing higher bits.
2. Compute index using modulo
```text
index = hash & (n-1); // n = length of table (always power of 2)
why power of 2?
because:
hash%tableSize == hash&(tableSize-1)  -> This is faster than modulo
```
3. Check bucket

if bucket is empty->insert new node<br>
if key already exists -> update value<br>
if collision-> add to LinkedList or Tree<br>

---

## Collision Handling
When two keys map to the same index -> collision<br>
HashMap uses:<br>
LinkedList chaining<br>
before Java 8<br>
Red-Black Tree<br>
After Java 8(when list becomes too long)

---

## When does HashMap convert LinkedList to Tree?

**Treeification Threshold = 8**

When a bucket has >= 8 nodes, HashMap tries to convert it to a Read-Black Tree.

**But Treeification doesn't happen always**

Java 8 requires : Bucket Size>=8 and table size >=64

if table size <64 -> it resizes first instead of treeifying<br>
Reason: resizing usually reduces collisions -> no need for tree

---

## Why Red-Black Tree?

LinkedList search time = O(n)<br>
Tree search time = O(log n) 

So worst-case performance improves

---

## What happens in get(k)?

Steps:
1. Compute Hash
2. Compute bucket index
3. Go to bucket
4. if bucket is : LinkedList -> scan list or Tree -> tree search(log n)
5. Compare keys using:
```text
(key==node.key || keys.equals(node.key)
```

## Resizing(Rehashing)
Load factor = 0.75(default)

when : size> capacity *loadFactor, hasmap doubles the size of the table

Rehashing is expensive -> O(n)

Java 8 optimized rehashing:
1. Node either stay in same bucket OR move to bucket oldIndex + oldCapacity
2. No need to fully recompute

## Why HashMap is Not thread-safe

Multiple threads modifying the same structure can cause:
1. Lost updates
2. infinite loop(Only before Java 9 due to list reversal issue)
3. inconsistent data

Use:
1. ConcurrentHashMap
2. Collections.synchrozinedMap(...)

## Hashmap interview questions 
>Why bucket size for treeification is 8?

**"The choice of 8 is driven by a trade-off between memory efficiency, probability, and security."**

1. **Probability (The Math):** According to the JDK source code, bucket collisions ideally follow a Poisson distribution. With a good hash function, the probability of 8 elements landing in the exact same bucket is roughly 1 in 10 million. If a bucket hits 8, it signals a fundamentally bad hash function or a deliberate attack.
2. **Memory Trade-off:** A Red-Black tree node (`TreeNode`) is roughly twice the size of a standard linked list `Node`. Java delays treeification until the bucket hits 8 to avoid unnecessary memory bloat for normal, well-distributed maps.
3. **The SDE 2/3 Caveats:** Reaching 8 doesn't guarantee treeification. The map's total capacity must also be at least 64 (`MIN_TREEIFY_CAPACITY`); otherwise, the map simply resizes. Also, if the bucket size drops to 6, it reverts to a linked list to prevent performance thrashing (hysteresis).
4. **The Real World "Why" (Security):** This mechanism was introduced in Java 8 to mitigate **HashDoS (Denial of Service) attacks**. If an attacker feeds thousands of colliding keys, the map degrades to $O(\log n)$ search time instead of a catastrophic $O(n)$ linked list traversal.
